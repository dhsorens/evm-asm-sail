# PROGRESS

Live plan and status for `evm-asm-sail`. We work through this incrementally; check items off
as they land, and revise milestones as we learn.

## Goal

Prove [`evm-asm`](https://github.com/Verified-zkEVM/evm-asm) correct with respect to the EVM
specification extracted into Lean from [`evm-sail`](https://github.com/frisitano/evm-sail)
(Sail → Lean, via the Sail Lean backend).

evm-asm proves its RV64 zkEVM guest against an *internal, untrusted* Lean port of the
execution-specs ("SpecRef", `EvmAsm/Stateless/SpecRef/`), and its README explicitly solicits an
external Lean specification to break that circularity — naming evm-sail as the intended
complement. This repo builds that bridge: the extracted evm-sail spec on evm-asm's toolchain,
plus the equivalence proofs connecting it to SpecRef, bottom-up.

## The lay of the land (surveyed 2026-08-12)

Upstream `evm-sail` now ships a complete, maintained Lean extraction — far beyond where it was
in June:

- `extractions/lean/src/` — the **committed generated model** (package `evm`, lib `Evm`,
  73 modules / ~32k lines, toolchain `v4.29.0`), regenerated by `make extract-lean` using a
  **custom Sail compiler** ([frisitano/sail@evm-sail](https://github.com/frisitano/sail/tree/evm-sail));
  upstream Sail is explicitly unsupported for regeneration.
- `extractions/lean/contract/HostAxioms.lean` — the hand-maintained host contract (~2.5k lines):
  the generated model runs in `StateT HostState Evm.Defs.SailM`, an **executable** Lean host
  (byte arrays, assoc-list stores, journal frames). Only genuine crypto accelerators remain
  opaque (`nativeAccelerateBytes`, linked from C in the runner).
- `extractions/lean/runner/` — builds the extraction into a shared library behind the same ABI
  as the native harness, so the Lean model runs the retained fixture corpus
  (tests-zkevm v0.6.2, 26,104 stateless input/output pairs) **byte-exact** against EELS.
- An extensional world-state contract (`Evm.Contracts`) already gives the host operations an
  implementation-independent meaning — exactly the axiomatic layer we'd planned to write.

Consequences for this repo:
- We do **not** write an extraction pipeline, extern stubs, or a pure-Sail host — upstream did
  all three (better). The old plan's M0 extraction work and M2 (pure host) are obsolete.
- Our contribution is the **integration + proofs**: one Lake project holding evm-asm (git dep)
  and the upstream extraction (submodule path dep) on one toolchain, and the
  SpecRef ↔ `Evm` equivalence theorems.
- evm-asm origin/main (`6a43f7d`, 2026-08) is still on `v4.30.0-rc1`, still has SpecRef, and
  still solicits the external spec. The extraction pins `v4.29.0` → the "bump" is building it
  under `v4.30.0-rc1` in our root project (validated for lean-sail + generated code style;
  full-package check in progress).

- **INVALID** (0xfe) is **done** — `invalid_step_equiv`
  (Opcodes/Invalid.lean). The earlier reading here was wrong: it said the
  byte was MM-3-blocked like the CALL/CREATE family because
  `opImplementation`'s catch-all throws inside the `partial mutual` block
  and there is "no `def` to target". But `throw (.invalidOpcode op)` names
  nothing in that block — it is a total expression, so it runs and the
  theorem targets it inline. What blocks the CALL/CREATE family is that
  their *handlers* are `partial def`, which is a different fact from the
  dispatch match being `partial`. The row is `full`, not `n/a (MM-3)`.

  One reachable outcome, and the double-fault class is empty **by proof**
  rather than by case split: `opcode_stack_effect (.INVALID ()) = pure
  (0, 0)`, so `execute`'s hoisted `validate_stack` cannot fire, and
  SpecRef reads nothing and charges nothing before throwing. MM-4 is
  vacuous (neither side moves the pc), and there are no new assumptions —
  `StateRel` is the only hypothesis. The theorem quantifies the byte, so
  it covers the whole undefined range: the extraction's decoder collapses
  every byte with no `ast` constructor onto this node.

  M1's opcode-by-opcode work is now complete apart from the six-member
  MM-3-blocked CALL/CREATE family.

- [x] `Coverage/Exhaustive.lean` — the exhaustive step theorem's first
      tranche, and the first statement in the tree quantified over
      `Evm.Defs.ast` rather than written per opcode.

      The gap it closes is one nothing had named. Every opcode theorem
      states its *own* AST-constructor-to-handler pairing, and nothing
      compares those statements: `add_step_equiv` would be exactly as
      green if it related `iMul` to `.ADD ()`, because the two sides only
      ever meet inside the statement a human wrote. The intended pairing
      lived in a `docs/opcode-coverage.md` column that nothing read.
      `baseHandler` makes it a table and `baseHandler_step_equiv`
      discharges all 28 entries from it, so a mistranscribed arm is a
      failed `exact` — checked by canary, which is the only way to know a
      guard of this kind actually bites.

      **The tranche is chosen by signature, not by confidence.** It is
      the 28 opcodes whose theorem needs nothing beyond `StateRel` and the
      MM-4 pc convention and whose post is `BasePost`: the ALU core
      (binops, unops, ternops, EXP), POP and JUMPDEST. Surveying all 87
      landed step theorems is what identified it — 62 land in
      `BasePost mem`, but only 30 carry no further hypothesis, and STOP
      (`StopPost`, no pc hypothesis) and INVALID (its post is a variable
      and its handler an inline `throw`) leave 28 sharing a statement
      exactly. The other 53 need an opcode-indexed pre/post family, which
      is the next installment rather than this one.

      **What it does not close is MM-3**, and the entry now says so
      precisely. The theorem relates `runR (baseHandler op)` to
      `runS (execute op …)`; it does not say SpecRef's dispatch sends `op`
      to `baseHandler op`, and nothing can while `opImplementation` is a
      `partial def`. So the transcription is still a reading — but one
      reviewable object instead of 28 uncompared statements, and the
      object that becomes a theorem the day upstream de-partials.
      Ledgered as **Dispatch fidelity** in `Assumptions.lean`.

      Two facts are computed rather than asserted: `baseOps_length = 28`
      (from the registry's verified `astCtors`, so the docstring's number
      cannot go stale and the theorem is visibly non-vacuous) and
      `baseHandler_full` (everything the table claims is already `full` in
      `astStatus` — the direction that matters, since it cannot quietly
      promote a row). Axioms: the usual three.

      One deliberate asymmetry with `astStatus`, argued in the docstring:
      `baseHandler` *does* close with a catch-all. Its default is
      `none` — not claiming — so a constructor added upstream silently
      leaves the tranche instead of silently joining it, and claiming
      still requires writing the constructor down. The totality discipline
      stays where it bites.
